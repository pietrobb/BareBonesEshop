# BareBones Shop

[![CI](https://github.com/pietrobb/BareBonesEshop/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/pietrobb/BareBonesEshop/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)
![PHP 8.1+](https://img.shields.io/badge/php-8.1%2B-777bb4.svg)

A dependency-free PHP e-commerce framework: server-side rendered storefront,
JSON API, and admin back-office. Runs on **SQLite** out of the box or **MySQL/
MariaDB** for production. Multi-language, multi-currency, extensible through
`extensions/` without editing core files.

No Composer dependencies, no build step — plain PHP 8.1+ and PDO.

**Status:** actively developed. Read the **Upgrade notes** in [CHANGELOG.md](CHANGELOG.md) before
updating an installation. Found a security problem? See [SECURITY.md](SECURITY.md) — please report
it privately, not as a public issue. Licensed under the [MIT License](LICENSE).

---

## Requirements

- **PHP 8.1+** (CLI + a web SAPI) with `pdo`, `pdo_sqlite` (or `pdo_mysql`),
  `mbstring`, `json`, `dom`, `libxml`; `sodium` is required for signed updates
- A web server (Apache with the bundled `.htaccess`, nginx, or the PHP built-in
  server for development)
- Optional: MySQL/MariaDB 10.4+ when `db_driver = 'mysql'`

## Quick start (development)

```bash
# 1. Checkout including the vendor/bbf (BareBonesForms) submodule
git clone --recurse-submodules <repository-url> shop && cd shop
#    (an existing checkout: git submodule update --init)

# 2. Install: creates config.php from config.example.php with a fresh
#    admin_identity_key, the private runtime directories next to the checkout
#    (../bareboneseshop-private: database, jobs, invoices, backups, logs),
#    the schema, admin forms and import templates, and the first owner account;
#    then prints the doctor checklist. Safe to re-run; never rewrites config.php.
BBE_ADMIN_PASSWORD='a-strong-password' php cli/setup.php install \
  --app-url=http://localhost:8080 --admin-username=admin

# 3. (optional) Seed demo data
php cli/seed.php --count=200

# 4. Serve — router.php applies the .htaccess deny/rewrite rules to PHP's
#    built-in server, which would otherwise serve config/, cli/ and releases/
php -S localhost:8080 router.php
```

Open <http://localhost:8080> for the storefront and
<http://localhost:8080/admin.php> for the back-office. The owner signs in with
the password from step 2 plus the TOTP code from the secret that `install` prints
once (store the recovery codes). Further accounts: `php cli/admin-user.php create`
(see [Admin identity](#admin-identity-queues-and-operations)). `cli/hash-password.php`
only produces a legacy `admin_password` hash, which stops working as soon as any
database admin account exists.

### Production web server

- **Apache**: the bundled `.htaccess` (needs `AllowOverride All` and `mod_rewrite`).
- **nginx + PHP-FPM**: [`deploy/nginx.conf`](deploy/nginx.conf) mirrors the `.htaccess`
  deny and rewrite rules. Keep its `location ~ \.php$ { try_files $uri @redirect; ... }`:
  store-prefixed scripts such as `/cs/api.php` do not exist on disk and reach PHP only through
  that fallback (set `operations.nginx_config` and `php cli/setup.php doctor` checks it).
- **Docker**: [`deploy/docker-compose.yml`](deploy/docker-compose.yml) runs nginx and the
  PHP-FPM image from [`deploy/Dockerfile`](deploy/Dockerfile) with the private runtime data
  on a named volume. PHP runs as `www-data` (uid 33) on a read-only root filesystem with the
  code mounted read-only; only `cache/`, `uploads/`, `import/` and `logs/` are writable and
  must be owned by uid 33. First run, through the opt-in installer that may write `config.php`:
  `docker compose -f deploy/docker-compose.yml run --rm -e BBE_ADMIN_PASSWORD=... setup php cli/setup.php install --app-url=http://localhost:8080 --admin-username=admin`,
  then `docker compose -f deploy/docker-compose.yml up -d`.

Never use `php -S` without `router.php`, and never for production.

### Configuration

All settings live in **`config.php`** (a single returned array, untracked; `install`
creates it from the tracked template `config.example.php`). Key entries:

| Key                | Purpose                                                        |
| ------------------ | ------------------------------------------------------------- |
| `db_driver`        | `'sqlite'` (default) or `'mysql'`                             |
| `db_sqlite_path`   | Path to the SQLite file (default `db/shop.sqlite`)           |
| `db_*`             | MySQL host/port/name/user/password (when `db_driver=mysql`)  |
| `admin_identity_key` | Encrypts admin TOTP seeds (generated by `install`; or `BBE_ADMIN_IDENTITY_KEY`) |
| `admin_user` / `admin_password` | Legacy Basic-Auth fallback (`password_hash()` output), ignored once a DB admin account exists |
| `adapters`         | Legacy single-default search / queue / payment / VAT / storage backends |
| `provider_defaults` | Default stable codes for payment, mail, tax, and optional ERP |
| `providers`        | Additive code→adapter registry for concurrent payment/shipping/mail/tax/ERP providers |
| `outbound_webhooks` | Config-only signed webhook endpoints, event filters, stores, and secrets |
| `extensions` | Extensions loaded from `extensions/<code>/` without editing core files ([docs/EXTENSIONS.md](docs/EXTENSIONS.md)) |

Never commit real secrets (Stripe keys, admin password hash for production) —
keep them in an untracked local override or environment-specific config. The
machine-readable deployment contract is `config/config.schema.json`; fields marked
`x-secret` must be injected from deployment secret storage.

### Merchant setup and operations

```bash
php cli/setup.php install            # first install (see Quick start); idempotent
php cli/setup.php apply --json       # idempotently creates private runtime paths
php cli/setup.php doctor --json      # versioned checklist; does not print secrets
php cli/setup.php doctor --json --strict
```

The doctor checks runtime/extensions, config schema, store and DB readiness, private
paths, payment/mail/webhook configuration, worker/cron, backup, and the shipping/ERP
integration boundaries. Warnings identify operator staging work; failures include a
concrete remediation. `apply` never edits merchant/legal data or credentials.

Load balancers may use `GET /healthz` for process liveness and `GET /readyz` for DB,
store-config, and writable runtime readiness. Both return bounded JSON with an
`X-Request-ID`; no secret or exception detail is exposed. Application and worker
operations write JSON Lines with correlation/store/channel context to
`structured_log_file`, recursively redacting secret-shaped fields.

The built-in `http-carrier` provider implements a versioned HTTPS rates → pickup
points → label → cancel → tracking lifecycle. The `http` ERP provider implements
product/customer/order export, status updates, stock pull, and health. Configure
them under `integrations.http_shipping` / `integrations.http_erp`; fixture contract
tests run without credentials, while a live sandbox smoke remains an explicit
operator step before production.

Checkout offers a pick-up point list for every rate whose carrier implements that
lifecycle (`ShippingLifecycleAdapter::pickupPoints`) and whose shipping method has
`supports_pickup` (a point is optional) or service type `pickup` (a point is
required). The chosen point is validated against the carrier's list, kept in the
order's shipping snapshot and passed to the label as `pickup_point_id`. Packeta
reads its points from the official v5 branch feed stored locally; refresh it 1–4×
a day with `SHIP_PACKETA_API_KEY` set, e.g.
`23 7,11,15,19 * * * php cli/packeta-pickup-points.php SK CZ`. Without a synced
feed Packeta offers no points.

A company buyer fills the optional `company`, `ico` (company ID), `dic` (tax ID)
and `vat_id` (EU VAT ID) fields of the checkout form or JSON body. Any ID requires
the company name; IDs of an invalid format are refused. They are stored on the
order address and printed on the invoice; a VIES-valid VAT ID from another EU
member state makes the order reverse charge. A B2B member's form starts with the
company's legal name, registration number and VAT ID.

An unpaid bank-transfer order shows payment instructions on the order-done page, in
the customer's order detail and in the order confirmation e-mail, and returns them as
`bank_transfer` in the JSON checkout response: beneficiary, IBAN, BIC, exact amount,
variable symbol (the order ID, also shown in admin *Awaiting payment*), message and
due date. The account comes from `legal.name`, `legal.iban`, `legal.bic` and the
optional `legal.bank` of the store in `stores.json`; without a valid IBAN no
instructions are shown. EUR orders also get a PAY by square QR code, generated
locally as an inline SVG.

## External API v1 and event webhooks

The machine API is served below `/api/v1` and is separate from the browser-oriented
`api.php`. It uses store-bound bearer credentials and scopes, opaque cursor
pagination, stable DTOs, and a required `Idempotency-Key` on every mutation. The
complete contract is [`docs/openapi.yaml`](docs/openapi.yaml).

```bash
php cli/migrate.php
php cli/api-client.php create --name=ERP --store=default \
  --scopes=products:read,products:write,orders:read
php cli/api-client.php list
php cli/api-client.php revoke --key=<12-hex-key-id>
```

Resources and scopes: products (`products:read`, `products:write`), orders
(`orders:read`, status changes and shipments `orders:write`; a move to `refunded`
also needs `refunds:write`), categories (`categories:read`), customers without
credentials (`customers:read`) and per-warehouse stock with ledger adjustments
(`inventory:read`, `inventory:write`). Every credential sees only its own store.

The create command prints the token once; only its SHA-256 hash is stored. Never
put a token in a URL, log, repository, database export, or webhook payload.
Commerce mutations write CloudEvents-compatible records to `event_outbox` in the
same database transaction. `cli/worker.php` signs each configured delivery with
`X-BBE-Event-ID`, `X-BBE-Timestamp`, and `X-BBE-Signature`, retries non-2xx
responses with exponential backoff, and moves exhausted events to `dead` after
eight attempts. Endpoint URLs and secrets live only in deployment configuration;
endpoints must use `https://` (plain `http://` only with `'allow_insecure_http' => true`
for a receiver on a trusted local network) and a secret of at least 32 bytes.

## Catalog pricing, promotions, and B2B

Migration `20260801190000_catalog_pricing_b2b` preserves each legacy
`products.category_id` as the primary assignment and adds brands, additional
categories, GTIN/MPN, integer-cent cost, variant media, dimensions, availability,
store/currency/group price lists, and time-bounded promotions. Price-list and
promotion choices are copied into each cart/order item's `_pricing` snapshot; the
existing financial snapshot remains the authority for totals and tax.

DB price lists take precedence over the legacy `pricing.json` group fallback.
Promotion priority is deterministic; `exclusive` stops after the first applied
rule and `stack` continues in priority order. Supported cart actions include fixed
or basis-point discounts, free shipping, buy-X-get-Y, and explicit gift
entitlements. Gift rules never silently decrement stock: fulfillment must turn the
entitlement into a reviewed order line.

B2B invoice purchase is fail-closed. The `invoice` method is offered only to a
logged-in customer linked to an active, approved company with invoice purchase
enabled, positive payment terms, and enough remaining integer-cent credit. Company,
group, price-list, and customer resolution is always bound to the active store;
company VAT validation remains an input to the canonical VAT snapshot rather than
a substitute for legal review.

## Inventory ledger and split fulfillment

Migration `20260801200000_inventory_ledger_fulfillment` adds store-scoped immutable
`stock_movements`, supplier/PO receipts, explicit `deny`/`backorder`/`preorder`
policies, bundle component snapshots, personalization requirements, and warehouse-
split `shipments` with `shipment_items`. Every count, feed sync, reservation,
release, receipt, shipment, and return records its delta and resulting on-hand and
reserved balances. Exact guards reject oversell, double release, duplicate receipt,
and duplicate shipment consumption.

`Inventory::createPurchaseOrder()` enforces supplier minimum and pack size;
`Inventory::receivePurchaseOrder()` requires an idempotency key. `Fulfillment::planOrder()`
creates one shipment per frozen warehouse allocation, while `Fulfillment::ship()`
can dispatch them independently. A final whole-order shipment fails closed while
backordered units remain. Prices and taxes remain on the unchanged order-item and
financial snapshots; bundles affect only the auditable physical allocation layer.

## Partial returns, exchanges and credit notes

Migration `20260801210000_returns_credit_notes` adds store-scoped return labels,
idempotent partial receipts, explicit `restock`/`discard`/`repair` decisions,
exchange reservations, item refund batches, and immutable credit-note lines. Multiple
RMAs may be open for one delivered order, but all non-rejected requests share an
exact ordered-quantity cap. Only received quantities can be exchanged or credited.

`InvoiceService::credit()` derives every integer-cent gross/net/VAT amount from the
original invoice financial snapshot by deterministic prefix allocation. Replays
return the original credit note, pending or completed refunds reserve their item
quantity, and the worker marks partial payment refunds without closing the whole
order. A restock follows the frozen shipment allocation and records a G7 ledger
movement; discard and repair never change on-hand stock.

## Admin identity, queues, and operations

Migration `20260801220000_admin_identity_queue_operations` adds database-backed
admin accounts, encrypted TOTP seeds, one-time recovery codes, store grants,
tracked devices, revocable server-side sessions, and a durable database queue.
Once any DB account exists, legacy config/JSON credentials no longer authenticate.
`php cli/setup.php install` generates `admin_identity_key` into a new `config.php` and
can create the first owner. Otherwise generate the deployment-only encryption key
and first owner from the CLI; password input is accepted only through the process
environment:

```bash
php cli/migrate.php
php cli/admin-user.php keygen
BBE_ADMIN_IDENTITY_KEY=<secret> BBE_ADMIN_PASSWORD=<secret> \
  php cli/admin-user.php create --username=ops --role=owner --store=default
```

**Delegated admin management.** Owners can manage every account (except the owner
protections). A non-owner with `admins.manage` may only create or manage accounts
whose role permissions are a subset of its own, in every store the target account
is granted; the create form lists only those roles. It cannot change its own role,
status or store grants, but may reset its own password/MFA and revoke its own sessions.

Set `queue.backend` to `file`, `database`, or `redis`. File mode retains the
single-worker lock; database and Redis modes use opaque atomic claims and leases
so multiple workers may run concurrently. In every mode a job whose worker died
mid-run counts as a failed attempt once its lease expires (file mode: 300 s in
`processing/`) and is dead-lettered after three attempts. Jobs, mail, audit records, and outgoing
webhooks carry correlation IDs. The store-scoped admin dashboard shows bounded
failed-job, mail, payment, and webhook incidents without exposing secrets.

## Themes, content, marketing, and quality gates

Migration `20260801230000_theme_content_marketing` adds store-scoped menus, scheduled
banners, landing-page SEO fields, and exact-path redirects. Each store selects a
package with `theme` in `stores.json`; every package has a private `theme.json`,
optional block overrides under `blocks/`, public versioned assets under `assets/`,
and explicit CSS/JS/block byte budgets. `Template::document()` is the shared
accessible SSR shell; the fallback chain remains store → theme package → legacy
theme block → base block.

Page layouts come from several `layouts.json` files merged by `Template::loadLayouts()`, later
files winning: the root `layouts.json` (base layouts and pages for the legacy `blocks/`), then
each theme in the inheritance chain from the root ancestor down to the active theme
(`themes/default/layouts.json` first, a child theme's after it), then the store override
`blocks/stores/<store>/layouts.json`. Objects merge key by key, so a theme can redefine one page
(the default theme maps `homepage`, `product`, `cms`, `account` and `wishlist` to its
`storefront` layout) and keep the rest; arrays such as a page's `sections` or a layout's `slots`
are replaced as a whole, never appended.

The **Content & Marketing** admin page publishes menus, banners, landing pages, and
301/302/307/308 redirects with CSRF, store permissions, validation, sanitization,
and audit records. `/feeds/google.xml` and `/feeds/meta.csv` export the active store
catalog from integer-cent prices; set an absolute `app_url` before enabling them.
Analytics integrations subscribe to the first-party `barebones:consent-ready` event,
which is not emitted until analytics or marketing opt-in exists.

Spanish (`es`) is included and every locale has exact key parity. Run the same gates
as CI before deployment:

```bash
php cli/i18n-parity.php
php cli/quality-gates.php
php cli/static-analysis.php
cli/phpstan.sh            # PHPStan level 5 exactly as CI: pinned phar, clean `git archive HEAD` copy
```

`cli/phpstan.sh` analyses the committed tree only (commit first) and must report no errors. The
baseline (`phpstan-baseline.neon`) can only shrink: an entry that no longer matches fails the run,
so a fix that removes a baselined finding deletes its entry in the same change.

The quality gate verifies package paths, declared byte budgets, WCAG 2.2 AA skip/focus/target-size/reduced-motion/forced-colors invariants, feed routes, consent defaults, and runs `php cli/theme-check.php`.
`php cli/update.php check|backup|apply` and `doctor --package` run the same theme gate automatically before anything changes: the **new core from the package with the installed themes, stores.json and store block overrides** (see [Production updates](#production-updates)). Testing the bundled default theme alone does not qualify a custom theme; do not update production first to run this check. For a manually assembled tree, run `php cli/theme-check.php` (nonzero exit on incompatibility) and `php cli/staging-preflight.php --strict` in it.
The theme probe uses the candidate's real checkout presenter and renderer with an in-memory fixture database: physical/digital/mixed carts, redisplay, required fields, country options, escaping, shipping/payment choices, consents and errors. It does not place orders, send mail or call payment gateways. `php cli/test-theme-contract.php` verifies the legacy Aeon regression and deliberately broken templates; `php cli/test-theme-upgrade-gate.php` proves an incompatible upgrade is refused with files and database unchanged. Both run in the canonical test suite.
This is a checkout contract gate, not a full theme certification: it does not prove browser JavaScript, visual/accessibility parity, other pages than checkout, store-specific configuration (currency, shipping zones, payment providers), actual payment/webhook delivery or migration/rollback safety. Browser, payment and assistive-technology checks still complement it. Deployments that copy files directly instead of using `cli/update.php` are not intercepted.

## Migrations

Schema changes are **forward-only**, file-based, and checksum-verified. There is
no `down()` — to revert, write a new migration.

```bash
php cli/migrate.php             # apply all pending migrations
php cli/migrate.php status      # show applied / pending / checksum state
php cli/migrate.php create add_foo_table   # generate a stub migration
php cli/migrate.php baseline    # mark current files as applied (no run)
```

By default a backup labelled `pre-migration` is taken before any pending
migration runs (configurable via the backup service). Migration files live in
`migrations/` and are named `YYYYMMDDHHMMSS_description.php`, each returning an
anonymous class with an `up(PDO $db, bool $isSqlite)` method that keeps
SQLite/MySQL parity.

### Backups and restore

```bash
php cli/backup.php --gc                       # cron: database copy + <backup>.files.tar, then retention GC
php cli/restore.php --list
php cli/restore.php <backup.db>               # SQLite: verified swap under the maintenance gate
php cli/restore.php <backup.sql> --i-stopped-writers   # MySQL/MariaDB: scratch database first, then live
php cli/restore.php <backup> --files[-only] [--force]  # invoices, uploads, GDPR salt
```

Restores verify the backup's SHA-256 and size and take a `pre-restore-snapshot`
first. The `.files.tar` archive holds the GDPR salt, the secret behind every
pseudonymised GDPR record: keep backups on encrypted, access-controlled storage.
Grants, the scratch database and the files-overwrite rules are in the
[operations runbook](docs/OPERATIONS_RUNBOOK.md#restoring-with-clirestorephp).

## Production updates

Updates are distributed as versioned delta directories. Every changed path has
both its expected old hash and new hash, so a customer-modified core file is
reported as a conflict and is never overwritten. `config.php`, `.env`, runtime
data, uploads, databases, logs, and per-deployment version state cannot be part
of a package.

```bash
# Release side: one-time key generation; keep the secret key offline
php cli/build-update.php keygen --public=/secure/update-public.key \
  --secret=/secure/update-secret.key

# Compare two clean release trees and sign the manifest
php cli/build-update.php --from=/releases/1.0.0 --to=/releases/1.1.0 \
  --base-version=1.0.0 --version=1.1.0 --output=/releases/update-1.1.0 \
  --secret-key=/secure/update-secret.key

# Shop side: verify server capabilities before changing anything
php cli/update.php doctor

# One-time adoption for a pre-updater install (only after identifying it)
php cli/update.php baseline --version=1.0.0

# Verify the signed package against the identified installation
php cli/update.php doctor --package=/releases/update-1.1.0

# Inspect first, then apply (apply always creates a snapshot)
php cli/update.php check --package=/releases/update-1.1.0
php cli/update.php apply --package=/releases/update-1.1.0
php cli/update.php list
php cli/update.php rollback --snapshot=20260801120000-abcdef123456
```

Set `update_public_key` and `update_storage_dir` in `config.php`; installed
version metadata and rollback snapshots stay in that private directory. Existing
pre-updater shops require one explicit `baseline` after their deployed release
has been identified. Run `doctor` on each deployment before its first update; it
checks PHP/sodium, the public key, private storage and locking, database health,
a real database backup/restore probe, and (when supplied) the signed package's
compatibility with installed files. `doctor --json` is suitable for deployment
automation. Packages are Ed25519-verified and unsigned packages are refused
unless the operator supplies `--allow-unsigned` explicitly. Rollback refuses to
overwrite files changed after an update unless `--force` is supplied after
manual review. Rolling back an update that ran migrations restores the
pre-update database and loses every order and other write made since then, so
it is refused with a warning unless `--accept-data-loss` is supplied.

Before any file, snapshot or migration changes, the updater assembles a private
candidate in `update_storage_dir` (installed code, themes, `blocks/`,
`stores.json`, overlaid with the package; never `config.php`, databases, uploads
or storage) and renders checkout with the new core for every installed theme and
store. An incompatible theme or store block override is a `[BLOCK]` naming the
theme/store, block, scenario and the field to fix, e.g.
`aeon / store default / storefront/checkout / physical [countries]: ... Render
country_options ...`. There is no bypass flag: fix the installed template (or
ship the fix) and rerun `check`. An updater older than this gate cannot run it, so
for that first hop run the gate from the trusted new release tree:
`php /releases/X.Y.Z/cli/theme-check.php --installed=/var/www/shop --package=/releases/update-X.Y.Z`.

Code-only packages support SQLite, MySQL, and MariaDB. Migration packages use a
verified SQLite snapshot or, on MySQL/MariaDB, a transactional dump that must
successfully restore into a guarded disposable `*_update_probe` database before
any files change. See the standalone [AI update runbook](docs/AI_UPDATE_RUNBOOK.md)
for the v1.8.0 bootstrap, production state machine, MySQL privileges, maintenance
window, evidence, and rollback procedure.

## Tests

A zero-dependency test runner (no PHPUnit) covering services, the JSON API,
migrations, and an optional HTTP smoke pass.

```bash
mkdir -p db          # the runner writes db/test.sqlite
php cli/test.php
```

- Exit code is **0** when all tests pass, **1** on any failure.
- The **HTTP smoke** block self-skips when no server is reachable at
  `SMOKE_URL` (default `http://localhost:8080`) — so the suite runs fully
  headless in CI. To include it locally, start `php -S localhost:8080 router.php` first.
- To test against MySQL, set `TEST_MYSQL_DSN` (and `TEST_MYSQL_USER` /
  `TEST_MYSQL_PASS`).

## Features

**Storefront** — catalog with categories, parametric/full-text search, product
detail with variants, cart, multi-step checkout, multi-language &
multi-currency, immutable quote→order→payment→invoice→OSS VAT snapshots, coupons, SEO pack (dynamic `sitemap.xml`,
`robots.txt`, JSON-LD: Organization / WebSite searchbox / BreadcrumbList /
Product / AggregateRating). Absolute SEO URLs come from `app_url` only, never from
the request `Host` header; without `app_url`, `sitemap.xml` answers 503 and
`robots.txt` omits its `Sitemap:` line.

**Customer accounts** — registration, login, password reset, addresses, order
history, invoices, GDPR self-service (data export + erase), product reviews,
**wishlist**, and **returns/RMA** requests.

**Admin back-office** — products, orders & fulfilment, invoices, warehouses &
stock, shipping/payment pricing engines, feeds/import, CMS pages, GDPR tools,
review moderation, RMA processing, and **customer management** (search, status
toggle, per-customer orders/addresses/RMA). Role-based access control.

**JSON API** (`api.php`) — 36 actions with rate limiting, CSRF on mutating
requests, registry-routed payment/shipping webhook endpoints, and a CSP violation report endpoint.

**Operations** — store-scoped provider registry for concurrent payment, shipping,
ERP, mail, and tax adapters; legacy single-adapter config remains supported. The
file queue freezes provider codes in order snapshots so retries use the original
provider. Merchant doctor/apply, config schema, liveness/readiness, structured JSON
logs, and complete generic HTTPS shipping/ERP contracts provide an AI-first
production path. Backups, migrations, and CLI tools live under `cli/`.

## Continuous integration

`.github/workflows/ci.yml` runs on every push and pull request:
